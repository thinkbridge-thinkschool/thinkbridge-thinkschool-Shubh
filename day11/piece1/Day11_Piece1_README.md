# Day 11 — Profile a Slow Endpoint

## Objective

Profile a deliberately slow API endpoint and identify the main data-access problems affecting its performance.

This exercise demonstrates two common EF Core performance issues:

1. The N+1 query pattern.
2. A missing database index.

The endpoint was profiled under load using k6, and the generated SQL and SQLite execution plan were captured before making any optimization changes.

## Approach

The approach was to intentionally create a slow read endpoint first and measure its baseline performance.

The steps were:

1. Reuse the existing Week-1 `QuotesApi`.
2. Add a deliberately slow endpoint that loads users first and then loads quotes separately for each user.
3. Run the endpoint and inspect the SQL generated by EF Core.
4. Use SQLite's `EXPLAIN QUERY PLAN` to inspect how the quote lookup is executed.
5. Run a 30-second k6 load test with 10 virtual users.
6. Record the baseline p50 and p99 latency.
7. Identify the two biggest performance problems.

No optimization was applied before collecting the baseline measurements.

## Slow Endpoint

The endpoint added for the exercise is:

```text
GET /api/performance/slow
```

The endpoint first loads all users:

```csharp
var users = await db.Users
    .AsNoTracking()
    .ToListAsync(cancellationToken);
```

It then queries quotes separately for every user:

```csharp
foreach (var user in users)
{
    var quotes = await db.Quotes
        .AsNoTracking()
        .Where(q => q.UserId == user.Id)
        .ToListAsync(cancellationToken);
}
```

This intentionally creates an N+1 query pattern.

## 1. N+1 Query Problem

The first query loads the users:

```sql
SELECT "u"."Id", "u"."Email", "u"."PasswordHash"
FROM "Users" AS "u"
```

EF Core then executes a separate query for each user:

```sql
SELECT "q"."Id", "q"."Author", "q"."IsDeleted", "q"."Text", "q"."UserId"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted") AND "q"."UserId" = @user_Id
```

With 2 users in the current database, the endpoint produced approximately:

```text
1 query → Users
2 queries → Quotes
-------------------
3 SQL queries
```

The general pattern is:

```text
1 + N queries
```

where `N` is the number of users.

As the number of users grows, the number of database round trips grows with it.

## 2. Missing Index

The quote query filters using:

```sql
WHERE "q"."UserId" = @user_Id
```

No suitable index was present on `Quotes.UserId`.

The SQLite execution plan was captured using:

```sql
EXPLAIN QUERY PLAN
SELECT "q"."Id", "q"."Author", "q"."IsDeleted", "q"."Text", "q"."UserId"
FROM "Quotes" AS "q"
WHERE NOT ("q"."IsDeleted") AND "q"."UserId" = 1;
```

The execution plan returned:

```text
SCAN q
```

`SCAN q` indicates that SQLite is scanning the `Quotes` table instead of using an index for the `UserId` lookup.

This becomes increasingly expensive as the `Quotes` table grows.

## Baseline Load Test

The endpoint was tested with k6 using:

```javascript
export const options = {
    vus: 10,
    duration: '30s',
    summaryTrendStats: [
        'avg',
        'min',
        'med',
        'max',
        'p(90)',
        'p(95)',
        'p(99)'
    ],
};
```

The request used during the test was:

```text
GET http://localhost:5177/api/performance/slow
```

### Baseline Results

| Metric | Result |
|---|---:|
| Virtual Users | 10 |
| Test Duration | 30 seconds |
| Total Requests | 184 |
| Success Rate | 100% |
| Average | 1.65 s |
| **p50** | **1.72 s** |
| p90 | 2.05 s |
| p95 | 2.13 s |
| **p99** | **2.28 s** |
| Maximum | 2.36 s |

The endpoint successfully handled all 184 requests during the test, but the latency was high for a simple read operation.

## Two Biggest Problems

### 1. N+1 Queries

The endpoint performs one database query to retrieve users and then another database query for every user.

This creates unnecessary database round trips and causes the amount of database work to grow with the number of users.

### 2. Missing Index on `Quotes.UserId`

The quote lookup filters by `UserId`, but SQLite reported:

```text
SCAN q
```

The absence of a suitable index means SQLite scans the `Quotes` table for the lookup.

## Why This Approach Was Used

The endpoint was intentionally kept inefficient so that the performance problems could be measured and demonstrated clearly.

The goal of this exercise was to establish a baseline rather than optimize the endpoint immediately.

The captured evidence includes:

- The slow endpoint.
- The N+1 SQL queries.
- The SQLite execution plan.
- Baseline p50 latency.
- Baseline p99 latency.

## What Did I Learn This Session?

I learned how to profile an API endpoint under load and connect application latency to database behavior. I also learned how the N+1 query pattern increases database round trips and how an execution plan can reveal a missing index.

## What Would Break This?

The endpoint would become increasingly slow as the number of users and quotes grows because the N+1 pattern increases database round trips and the missing `UserId` index causes table scans for quote lookups.
